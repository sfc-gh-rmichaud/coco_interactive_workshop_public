## What you will learn

- How to take a pipeline that exists as dynamic tables and express it as a dbt project that runs *inside* Snowflake, with no dbt infrastructure to host.
- Why an incremental model needs both a `unique_key` and a monotonic watermark, and what silently breaks when either is missing.
- Where dbt's guarantees are stronger than a dynamic table's, and where they are weaker.
- How to get the same project into CI, and what changes when a team is on dbt Cloud.

## Why this matters

Most teams arriving at Snowflake already have dbt. The question is never "dbt or dynamic tables" in the abstract -- it is "we have four hundred models and a Airflow box babysitting them; what does moving this into Snowflake actually change?"

This lab answers that on the smallest honest example: the *same* pipeline as lab 21, over the *same* raw data, built both ways. Lab 21's version is three dynamic tables where Snowflake owns the schedule. This version is three dbt models where you own it. Both are defensible. Knowing which properties you gain and which you give up is the point, and you cannot get that from a feature comparison table.

## The setup: deliberately the same data

`setup.sql` creates one raw landing table, `RAW_ORDER_EVENTS`, generated by byte-for-byte the same arithmetic and the same hash seeds as lab 21. That is not laziness -- it is what makes the comparison mean something. Your dbt models should agree with lab 21's dynamic tables row for row. If they do not, one of the two is wrong, and finding out which is a better exercise than any amount of reading.

The data is messy on purpose, in four ways:

- exact duplicate events, because delivery is at-least-once
- two different timestamp encodings in the same field
- missing customer ids on about 3% of rows, stored as JSON nulls
- a nested line-item array that needs flattening

It also creates a second schema, `LAB_DBT`, for dbt to write into. Keeping dbt's output away from its input means a bad run cannot damage the source, and you can drop the whole schema and start again.


Confirm you have the CLI's dbt support before starting, because the error if you do not is a bare "no such command":

```bash
snow --version      # 3.13 or later; 3.25+ if you want dbt_projects_profiles.yml handled by default
```

The last query prints your names. The confirm query before it should show:

| Metric | Value | Precision |
|---|---|---|
| `TOTAL_RAW_ROWS` | about 42,400 | within 1% |
| `DISTINCT_EVENTS` | 40,000 | exact |
| `DUPLICATE_ROWS` | about 2,400 | within 3% |
| `NULL_CUSTOMER_ROWS` | about 1,200 | within 3% |
| `NULL_CUSTOMER_WRONG_TEST` | **0** | exact |

> **Reading the Precision column.** *exact* means that number to the digit, on any
> date and in any account. *within n%* means the figure comes from a hash-based
> sample and moves slightly; anything inside the band is healthy. *guidance* means
> not reproducible -- an order of magnitude, not a target.

That last row is the JSON-null trap, and it matters more in dbt than it did in lab 21: a dbt `not_null` test on a column selected as `PAYLOAD:customer_id` **passes for every row**, because `OBJECT_CONSTRUCT_KEEP_NULL` stored a JSON null and a JSON null is a value. The test is green and means nothing. You need the cast.

## Steps

### Step 1 -- Have CoCo profile the raw table first (about 5 minutes)

Same opening move as lab 21. Do not skip it just because you know what is coming: the point is that the spec for the models comes out of the data, not out of your memory.

```
COCO_WS_LAB22_DB_<your_user>.LAB.RAW_ORDER_EVENTS is a raw landing table of storefront order
events in a VARIANT column. I am about to model it with dbt. Profile it and tell me every data
quality problem that would break a naive set of dbt models, with row counts and the evidence
for each. Be specific about the payload fields, and tell me which of these problems dbt tests
would catch and which they would not.
```

**What good looks like:** the four traps, with counts, and -- this is the part worth pushing on -- a straight answer on the last question. A good response says that `unique` and `not_null` tests catch the duplicates, that a `not_null` test on the raw VARIANT path does **not** catch the missing customer ids, and explains why. If it does not volunteer that, ask directly:

```
If I write a dbt not_null test on customer_id selected as PAYLOAD:customer_id, does it catch the
missing values? Show me the count both ways.
```

### Step 2 -- Have it scaffold the project (about 8 minutes)

```
Create a dbt project in ./dbt-lab22 that models COCO_WS_LAB22_DB_<your_user>.LAB.RAW_ORDER_EVENTS
into three models, writing to schema LAB_DBT of the same database:

  stg_order_events  one row per event_id, typed, deduplicated, keeping the most recently
                    ingested copy of each event
  stg_order_lines   one row per line item, flattened out of the nested items array
  cur_daily_sales   daily sales by channel and currency, counting cancellations and refunds
                    separately rather than netting them into the total

stg_order_events must be incremental. Add a sources.yml for the raw table and a schema.yml with
tests that would actually catch the problems you found in step 1. Warehouse COCO_WS_WH_<your_user>.
Explain your materialization choice for each model.
```

**What good looks like:** a project with `dbt_project.yml`, a profile file, three models and a `schema.yml`. Check four things specifically, because these are where a plausible-looking project goes wrong:

- **`unique_key = 'event_id'` on the incremental model.** Without it dbt appends, and step 5 will show you exactly what that costs. This is the single most important line in the project.
- **Both timestamp branches use `TRY_` functions.** Snowflake may evaluate both arms of a `CASE` regardless of the condition, so a plain `TO_TIMESTAMP_LTZ` in the `ELSE` fails the whole model on the numeric rows.
- **A cast on `customer_id`.** `PAYLOAD:customer_id::STRING` turns the JSON null into a SQL NULL. Without the cast, every downstream count of missing customers is zero.
- **The incremental filter's watermark.** See "if it goes sideways" below -- this one is nastier than it looks, and a model that gets it wrong still builds cleanly.

**If it goes sideways:** if CoCo puts `unique` and `not_null` tests on the raw source's `event_id`, that fails immediately and correctly -- the raw table genuinely has duplicates. Those tests belong on `stg_order_events`, after the deduplication. Ask it to move them and say why.

### Step 3 -- Deploy it as a dbt project object (about 6 minutes)

```bash
cd dbt-lab22

# Deploy. Name it fully qualified -- see the note below.
snow dbt deploy COCO_WS_LAB22_DB_<your_user>.LAB_DBT.coco_ws_lab22 \
  --source . -c <your-connection>
```

Three things will bite here, in this order. All three were hit while writing this lab:

1. **The profile's `role` is validated; `account` and `user` are not.** Leaving `role: placeholder` fails deployment with *"Role 'placeholder' does not exist or is not accessible."* Leaving `account` and `user` as placeholders is fine and is what you want in a committed file -- the project runs inside the account, so it needs no credentials. Put a real role in.
2. **Name the project fully qualified.** A bare name fails with `090105 (22000): Cannot perform CREATE TEMPSTAGE. This session does not have a current database.` The CLI stages the files before creating the object, and with no database in the connection there is nowhere to stage them.
3. **`-c` goes before the subcommand, not after.** `snow dbt execute <project> build -c <conn>` fails with `No such option: -c`, because everything after the dbt subcommand is handed to dbt, not to the CLI.

Then run it:

```bash
snow dbt execute -c <your-connection> \
  COCO_WS_LAB22_DB_<your_user>.LAB_DBT.coco_ws_lab22 build
```

**What good looks like:** `dbt build` runs the models and the tests together and ends with a summary line. On the reference project that is `Done. PASS=12 WARN=0 ERROR=0 SKIP=0 TOTAL=12` -- one incremental model, one view model, one table model and nine tests -- in about 14 seconds. Your node count will differ with the tests you wrote; what matters is `ERROR=0` and that the tests you added actually ran.

### Step 4 -- Check the models agree with lab 21 (about 5 minutes)

```
Query COCO_WS_LAB22_DB_<your_user>.LAB_DBT and tell me the row count of each of the three models.
Then tell me whether cur_daily_sales here would match the CUR_DAILY_SALES dynamic table from
lab 21 over the same raw data, and if there is any reason it would not.
```

**What good looks like:** these counts, on a fresh setup with no extra batches landed:

| Model | Rows | Precision |
|---|---|---|
| `stg_order_events` | 40,000 | exact |
| `stg_order_lines` | 80,000 | exact |
| `cur_daily_sales` | about 732 | within 2% |

The first is exact because deduplication is exact: 40,000 distinct events in, 40,000 rows out. The second is exact because every seeded event carries exactly two line items. The third is 61 dates times 12 channel-currency combinations; the 12 is structural and the date count shifts by one depending on where the 60-day generation window falls, which is where the 2% comes from.

A good answer on the comparison says yes, and that the reason is that both pipelines run the same SELECT over the same rows -- and then notes the honest asymmetry: lab 21's leaf refreshes on a `TARGET_LAG` that Snowflake enforces, while this one is exactly as fresh as the last time something ran `dbt build`.

### Step 5 -- Land new data, and watch the trap (about 8 minutes)

This is the step the lab exists for.

```bash
snow sql -f labs/22-build-a-pipeline-with-dbt/queries/land_new_batch.sql -c <your-connection>
```

That lands 4,000 genuinely new events **and re-delivers 200 events that are already in your model**. Raw goes to about 46,600 rows and 44,000 distinct events. Now build again:

```bash
snow dbt execute -c <your-connection> \
  COCO_WS_LAB22_DB_<your_user>.LAB_DBT.coco_ws_lab22 build
```

**What good looks like**, with a correct `unique_key`:

| Check | Value | Precision |
|---|---|---|
| `stg_order_events` rows | 44,000 | exact |
| duplicate `event_id`s in the model | **0** | exact |
| `stg_order_lines` rows | 84,000 | exact |

The 200 re-deliveries merged onto the rows already there. Lines rise by 4,000 rather than 8,000 because the new batch carries one item per event, not two.

**Now break it on purpose.** Remove `unique_key` from the model's config, redeploy, and build again after landing another batch. Measured on the reference project:

- the model gains **exactly 200 duplicate rows** -- one per re-delivered event
- **the model build still succeeds.** dbt reports the model as `OK created`
- the only thing that fails is the `unique` test on `event_id`: `Done. PASS=5 WARN=0 ERROR=1 SKIP=6 TOTAL=12`, with the six downstream nodes skipped because the test failed

Sit with that for a moment. The transformation was wrong, the run said SUCCESS for the model, and the only reason anyone finds out is a test somebody remembered to write. A dynamic table cannot make this mistake -- lab 21's `QUALIFY` runs over the whole table on every refresh -- and that is a real property you give up in exchange for incremental cost.

**If it goes sideways:** if the second build leaves the model at 40,000 rows when raw clearly has 44,000 distinct events, the incremental filter is the problem, not `unique_key`. Ask:

```
My incremental model did not pick up the new rows -- it is still at 40,000 while the raw table has
44,000 distinct events. The build reported success. What is my is_incremental() filter comparing,
and is that column monotonic in this data?
```

The answer, and it caught this lab's own reference project: `setup.sql`'s re-delivery pass stamps duplicates **90 minutes after** the row they copy, so the newest `INGESTED_AT` in the model can sit in the future relative to a batch that genuinely just arrived. `WHERE ingested_at > (SELECT MAX(ingested_at) FROM {{ this }})` then matches nothing at all, forever, and every run reports success. A watermark has to be monotonic in the order rows arrive; `RAW_ID` is, and a business timestamp usually is not.

## Check your work

```sql
-- Rebuild the per-user names, because a new worksheet is a new session.
SET NS     = (SELECT REGEXP_REPLACE(CURRENT_USER(), '[^A-Za-z0-9]', '_'));
SET LAB_DB = 'COCO_WS_LAB22_DB_' || $NS;
USE DATABASE IDENTIFIER($LAB_DB);
USE SCHEMA LAB_DBT;

-- One row per event, no duplicates, and every timestamp parsed.
SELECT COUNT(*)                                 AS MODEL_ROWS,
       COUNT(DISTINCT EVENT_ID)                 AS DISTINCT_EVENTS,
       COUNT(*) - COUNT(DISTINCT EVENT_ID)      AS DUPLICATES,
       COUNT_IF(OCCURRED_AT IS NULL)            AS UNPARSED_TIMESTAMPS,
       COUNT_IF(CUSTOMER_ID IS NULL)            AS MISSING_CUSTOMERS
FROM STG_ORDER_EVENTS;

-- The dbt project object itself, and its version history.
SHOW DBT PROJECTS IN SCHEMA;
```

Expected on a fresh setup with one `dbt build` and no extra batches: `MODEL_ROWS` and `DISTINCT_EVENTS` both **40,000** and `DUPLICATES` **0** (all exact), `UNPARSED_TIMESTAMPS` **0** (exact), and `MISSING_CUSTOMERS` about **1,140** -- that last one is the roughly 3% draw surviving deduplication, so treat it as within 3%.

`SHOW DBT PROJECTS` lists the project, the managed dbt runtime it is pinned to (`dbt_version`, 1.9.4 on the reference run) and its `default_version`. Worth knowing before you rely on rollback: repeated `snow dbt deploy` updates the project's **live** version rather than committing a numbered one, so `SHOW VERSIONS IN DBT PROJECT <name>` shows a single row with `is_live = true` and an empty `name`. Numbered versions you can roll back to come from `ALTER DBT PROJECT ... ADD VERSION`, or from Snowsight's redeploy. Check this on your own account rather than assuming a deploy left you a restore point.

## What just happened

You built the same pipeline twice and can now say precisely what differs.

**What dbt gave you that the dynamic tables did not.** Tests that live with the models and run on every build. `dbt build` running models and tests in dependency order, so a failing test stops what depends on it rather than letting bad data through -- that is what the six skipped nodes were. Project history and versioning on the deployed object, once you commit numbered versions. And a project that a team already knows how to review.

**What the dynamic tables gave you that dbt did not.** Freshness that Snowflake enforces rather than something you have to schedule. Incremental correctness for free: a dynamic table cannot silently append duplicates, because there is no watermark for you to get wrong. Fewer moving parts to be wrong about.

**What both required.** The `TRY_` functions on both `CASE` arms. The cast that turns the JSON null into a SQL NULL. Those are Snowflake behaviours, not tooling choices, and they bite identically either way.

The thing worth carrying out of this lab is that the incremental bug was invisible. It did not error, it did not warn, and it produced a number that looked entirely reasonable. The test caught it. That is the whole argument for writing the tests.

## Integrating with dbt at enterprise scale

The lab used a single small project deployed from a laptop. Here is what changes for a team, in the order it usually comes up.

**Bringing an existing project in.** dbt Projects on Snowflake runs dbt Core projects as-is. Point `snow dbt deploy --source` at the project directory. Most projects need no model changes -- what needs attention is the profile (Snowflake supplies the connection, so credentials come out) and any package dependencies, which need `dbt deps` run and an external access integration to reach the package hub. If both `dbt_projects_profiles.yml` and `profiles.yml` are present, **Snowflake uses the former and silently ignores the latter**; on CLI older than 3.25 you need `SNOWFLAKE_CLI_FEATURES_ENABLE_DBT_PROJECT_PROFILES_FILE_PRECEDENCE=true` to get that behaviour.

**Choosing a runtime.** Snowflake provides managed dbt Core and dbt Fusion runtimes. Pin one per project with `--dbt-version` at deploy time, or set an account default with `DEFAULT_DBT_VERSION`. Fusion is a Rust rewrite aimed at compilation time, which is the cost that hurts as a project grows past a few hundred models; it needs no license and no migration. Switching is a version toggle, so the sane approach is to measure your own compile time on both rather than take anyone's word for it.

**CI/CD.** Use the Snowflake CLI in whatever CI you already have -- GitHub Actions, GitLab and Azure DevOps are all supported, with OIDC rather than stored keys. The shape that works:

```yaml
# On a pull request: deploy to a dev target and prove the change builds and tests clean.
- run: |
    snow dbt deploy my_project --default-target dev
    snow dbt execute -c ci my_project build --select state:modified+ --defer

# On merge to main: deploy and run against prod.
- run: |
    snow dbt deploy my_project --default-target prod
    snow dbt execute -c ci my_project build
```

Never use `snow dbt deploy --force` in CI. It runs `CREATE OR REPLACE DBT PROJECT`, which destroys every version and the entire run history -- the two things you would want during an incident.

**Environments and secrets.** A Git-versioned `env.yml` holds per-environment variables and secret references, selected at run time with `--env` and overridden with `--env-vars`. This is the mechanism to reach for instead of maintaining parallel profile files per environment, which is how teams end up running dev models against prod.

**Orchestration.** A Snowflake task can run `EXECUTE DBT PROJECT` directly, which puts dbt in the same task graph as everything else in the account, with the same alerting and dependency handling:

```sql
CREATE OR REPLACE TASK RUN_LAB22_DBT
  WAREHOUSE = COCO_WS_WH_<your_user>
  SCHEDULE = 'USING CRON 15 * * * * UTC'
AS EXECUTE DBT PROJECT COCO_WS_LAB22_DB_<your_user>.LAB_DBT.coco_ws_lab22 ARGS = 'build';
```

Airflow still works if that is where your orchestration lives; the project object is just something to invoke. What you gain by using tasks is one less system to run.

**Observability.** Every model run feeds table- and column-level lineage into Horizon automatically, and run history, logs and artifacts are queryable in Snowsight. This is the part teams underestimate: lineage that includes the dbt models *and* everything downstream of them in one graph is not something a self-hosted dbt gives you.

**Where dbt Cloud stays the answer.** Be straight about this rather than pitching. The dbt Semantic Layer, the dbt MCP server, dbt Cloud's own IDE and scheduler, and any project spanning more than one warehouse are dbt Cloud features and do not move into Snowflake. Plenty of teams run both: projects whose models are entirely Snowflake move in, and the rest stay where they are.

**Cost.** Executions use a virtual warehouse and bill as normal compute. There is no per-seat or per-project fee, and Fusion costs nothing extra. Lab 62 will show you these runs as credits alongside everything else -- this lab's `QUERY_TAG` is `COCO_WS_LAB22`.

## Take it further

- **Make the two pipelines disagree, then find out why.** Run lab 21 and this lab in the same account, then join `CUR_DAILY_SALES` from each on `(sales_date, channel, currency)` and look for rows where the totals differ. On correct implementations there are none. Break one deliberately and see how fast the join tells you.
- **Add a snapshot.** Ask CoCo to add a dbt snapshot over `customer_id` so you keep history of when a customer first appeared. Then ask what the dynamic-table equivalent would be, and why it is more work.
- **Put a freshness test on the source.** `dbt source freshness` against `INGESTED_AT` gives you the alarm that `TARGET_LAG` gives you for free in lab 21. Compare what each one actually detects.
- **Have CoCo generate the documentation.** Point it at the deployed project object and ask for `sources.yml` and `models.yml` descriptions from the catalog metadata. It reads the deployed files, so it is describing what actually ran.

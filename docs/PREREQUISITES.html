CoCo Interactive Workshop

Prerequisites

Everything you need in place before the session, so the first lab starts on time. Budget about 20 minutes (guidance). Covers macOS, Windows, and Linux.

Do step 2 first, and do it early. Enabling cross-region inference needs an account administrator and is the single most common reason CoCo does not work on the day. Everything else you can do yourself in a few minutes.

What you are setting up

  • 1
    A Snowflake account with the privileges your chosen labs require You, or your admin
  • 2
    Cross-region inference enabled admin ACCOUNTADMIN only -- CoCo will not run without it
  • 3
    At least one CoCo surface Snowsight for browser labs; Desktop on macOS/Windows; VS Code or CLI on Linux
  • 4
    Snowflake CLI (snow) Used for data-lab setup and cleanup; not needed for local-only labs
  • 5
    A named connection, tested So snow sql -c <name> just works
  • 6
    The prerequisite check script, run once Tells you which labs your account supports

Short on time? Steps 1, 2 and 6 are the ones that matter. With those done you can run several labs entirely in the browser using CoCo in Snowsight, with nothing installed at all.

1. Snowflake account access

You need an account and a role that can create a database. Each lab builds its own database named COCO_WS_LABnn_DB and drops it again afterwards.

Use a non-production account. The labs create real account-level objects: one database per lab with sample schemas and seeded tables, a warehouse, and — depending on which labs you run — dynamic tables that refresh on a schedule, data metric functions that bill serverless credits until removed, masking policies, and (Lab 42 only) a Snowflake Postgres instance that bills continuously until dropped. Everything is namespaced with your user name and every lab has a teardown script, so nothing is shared and nothing is permanent, but a sandbox, dev or trial account is the right place to do this. So is the freedom to get things wrong.

Set up a dedicated workshop role (recommended)

  1. An administrator reviews 00_admin_role_setup.sql, sets WORKSHOP_ROLE and the actual ATTENDEE user, and runs the base grants. An existing customer role can be used instead. Do not use the administrator's user name for attendee resources.
  2. Choose optional bundles in that file for the selected labs: usage (43/62), lineage (12/72), data quality (23), task execution (33), and security review (52). They expose account-wide information or enable billable services; they are not automatically granted.
  3. The attendee selects the role in both CoCo and the SQL/CLI connection, then runs 01_role_smoke_test.sql. It disables secondary roles, creates uniquely named probe objects, and removes them. This prevents administrator privileges from hiding missing grants.
  4. The attendee runs 00_workshop_setup.sql under that same role. This creates their warehouse and run log; subsequent labs create their own databases. No role-management privileges are needed in this step.

The base role grants CREATE DATABASE, CREATE WAREHOUSE, USE AI FUNCTIONS, and the SNOWFLAKE.CORTEX_USER and SNOWFLAKE.COPILOT_USER database roles. The creator owns its databases, schemas and warehouse, so it can create lab tables, stages, file formats, views and apps there. It does not receive access to unrelated application data. A shared workshop role is not isolation between attendees: its members can access each other's role-owned objects. Use separate roles/accounts if isolation is required.

Already created objects as ACCOUNTADMIN? IF NOT EXISTS does not change their owner. Have an administrator inspect the exact attendee warehouse, database, schema and child-object grants. Transfer only workshop-owned resources after review, or clean up that attendee's disposable lab objects and rerun as the workshop role. A database ownership transfer alone does not transfer every child object. Never transfer production objects to fix a workshop.

Administrator-provisioned alternative: if account-level creation grants are prohibited, provision the exact attendee-suffixed names and grant the required warehouse rights and ownership/creation rights on the selected lab databases and schemas. Adapt scripts that use CREATE OR REPLACE DATABASE to the approved pre-created environment before the workshop. Merely granting warehouse USAGE is not enough to run the unmodified standalone setup scripts.

Fast path: ACCOUNTADMIN can run a disposable sandbox workshop if your organisation permits it. Do not use that shortcut in production. Prefer the dedicated role for daily work; run role-management and integration steps with an administrator. If neither is acceptable, use a presenter-led session or the seeded-data portions. Account policy, model access and cross-region restrictions still apply.

Ordinary cleanup must not drop the shared attendee role. After all attendees finish, an administrator can review 99_admin_role_cleanup.sql. See the Snowflake database-role reference for per-view access. USAGE_VIEWER is narrower than IMPORTED PRIVILEGES ON DATABASE SNOWFLAKE, which can expose organization-level information.

If none of your accounts are a good fit, ask your Snowflake team before you work around it. Two situations come up often: your non-production account inherits production's role model, so CREATE DATABASE and the governance privileges are not available to you; or your organisation would rather attendees did not hold elevated privileges in any account it owns. In either case your Snowflake sales engineer can provision temporary trial accounts for the session, in which you are the administrator and everything you build is disposable. It needs about a week's notice, so raise it as early as you can rather than on the day. Lab 42 is the only lab that will not run on a trial account.

2. Enable cross-region inference admin

Check this early. Verify permitted cross-region inference and model availability for the selected CoCo surface. Account defaults vary by provisioning date and policy; inspect the actual value rather than assuming DISABLED. Policy changes require administrator approval.

Check the current setting

Anyone can run this in a Snowsight worksheet:

SHOW PARAMETERS LIKE 'CORTEX_ENABLED_CROSS_REGION' IN ACCOUNT;

Read the value column:

ValueWhat it means
ANY_REGIONBroadest access and highest capacity. Nothing more to do.
AWS_US, AWS_EU, AZURE_US, AZURE_EU, GCP_US … Restricted to a cloud and geography. Verify that the models required by your selected surface are available in that boundary.
AWS_GLOBAL, AZURE_GLOBAL, GCP_GLOBAL Restricted to one cloud provider. Verify model availability; a non-disabled value alone is not proof of readiness.
DISABLEDCoCo will not work. This needs changing before the session.

Enable it

An ACCOUNTADMIN must run one of these. It can only be set at the account level -- not per user, not per session, and not by ORGADMIN.

-- Broadest model access and capacity (recommended for the workshop)
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'ANY_REGION';

-- Or keep inference inside one cloud provider
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'AWS_GLOBAL';

-- Or keep it inside one cloud and geography
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'AWS_EU';

What to tell your security team. Your stored data never leaves your account's region. During inference the prompt and the response transit to the processing region for the duration of the request and are not persisted there. Traffic within one cloud provider stays on that provider's private backbone; across providers it uses mutually authenticated TLS. Credits are billed in your own region, and there are no data egress charges.

Some newer accounts already have this on: for organisations created in commercial regions after 9 March 2026, ANY_REGION is the default, and a 2026_06 behaviour change sets a same-cloud default for many existing commercial accounts. Check rather than assume. Details: Cross-region inference.

While you have an admin's attention

Two other account-level things are worth confirming in the same conversation:

  • Cortex access. The SNOWFLAKE.CORTEX_USER database role is granted to PUBLIC by default. If your organisation revoked it, it needs granting back to your role.
  • Per-surface credit limits. A user needs a non-zero daily limit as well as the role. A value of 0 blocks that surface entirely: CORTEX_CODE_{CLI|DESKTOP|SNOWSIGHT}_DAILY_EST_CREDIT_LIMIT_PER_USER. Check the effective limit with your administrator; do not assume a permissive account default overrides a user-specific block.

3. Install a CoCo surface

Snowsight needs nothing installed and is recommended for browser-first labs, including workspace organization (74). Desktop is available for macOS and Windows, not Linux. Use it for the complete diagram export (12), local tooling (75), and other local-development walkthroughs. On Linux, use the Snowflake extension in VS Code for a local IDE, or CoCo CLI for a terminal. These are alternative surfaces, not identical interfaces; follow each lab's Surface row. Lab 73 teaches the IDE path without requiring Desktop.

CoCo Desktop

  1. Download the build for your chip from the CoCo product page -- Apple silicon and Intel are separate downloads.
  2. Open the .dmg and drag the app to Applications.
  3. Launch it and sign in to Snowflake when prompted.

CoCo CLI

curl -LsS https://ai.snowflake.com/static/cc-scripts/install.sh | sh

Then check it:

cortex --version

If cortex is not found, the installer put it in ~/.local/bin, which may not be on your PATH. Either use the full path ~/.local/bin/cortex, or add it:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

CoCo Desktop

  1. Download the installer from the CoCo product page. There are separate builds for Intel/AMD and ARM (Surface and similar), and each has a User installer (no admin rights needed) and a System installer (all users). Pick User unless your IT policy says otherwise.
  2. Run the .exe and follow the prompts.
  3. Launch it and sign in to Snowflake when prompted.

CoCo CLI

In PowerShell:

irm https://ai.snowflake.com/static/cc-scripts/install.ps1 | iex

Then close and reopen PowerShell so the PATH change takes effect, and check it:

cortex --version

If the script is blocked by execution policy, run PowerShell as your own user and allow the current process only:

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

That lasts for the current window only and does not change machine policy.

VS Code + Snowflake extension (recommended Linux IDE)

  1. Install VS Code for your Linux distribution using your approved software source.
  2. Open Extensions, search for Snowflake, and install the official Snowflake extension. Check the publisher and extension ID snowflake.snowflake-vsc.
  3. Open the Snowflake panel, sign in to your workshop account, and select the workshop role and warehouse.
  4. Open the workshop folder, select the CoCo icon, and start a chat. Ask it to execute SELECT CURRENT_ACCOUNT_NAME(), CURRENT_USER(), CURRENT_ROLE(), CURRENT_WAREHOUSE() and show the result and query ID.

A separate CoCo CLI installation is not required by the extension. Leave CoCo: CLI Path unset unless deliberately overriding its executable. See the extension documentation.

Optional standalone CoCo CLI

After reviewing your organisation's installation policy, follow the official CLI installer for Linux x64/arm64:

curl -qLsS https://ai.snowflake.com/static/cc-scripts/install.sh | sh
cortex --version
# If needed for this shell:
export PATH="$HOME/.local/bin:$PATH"

Persist PATH in your shell's startup file only if needed (for example ~/.bashrc for interactive bash). Snowsight is also available in your browser. Supported ACP editors are additional options; VS Code is the recommended path here, not the only IDE integration. See editor integrations.

CoCo in Snowsight -- nothing to install

Sign in at app.snowflake.com. CoCo appears inside Snowsight across Workspaces and Notebooks. This is the fastest way to confirm your account is set up correctly: if CoCo responds, the browser surface is reachable. Still run the role smoke test: a chat response does not prove the role can create lab objects.

4. Install the Snowflake CLI (snow)

This is a different tool from the CoCo CLI. snow runs SQL; cortex is the agent. Every lab uses snow to run its setup and teardown scripts.

Homebrew is the simplest route:

brew install snowflake-cli

That community formula updates automatically but can lag a release. For the Snowflake-maintained build instead:

brew tap snowflakedb/snowflake-cli
brew trust --cask snowflakedb/snowflake-cli/snowflake-cli
brew install --cask snowflake-cli

No Homebrew? Download the macOS package installer from the installation docs, or install it as a Python tool (needs Python 3.10+):

uv tool install snowflake-cli
# or
pipx install snowflake-cli

The Windows installer is the simplest route. Download it from the installation docs, run it, then open a new terminal so the PATH change takes effect.

Or install it as a Python tool (needs Python 3.10+):

uv tool install snowflake-cli
# or
pipx install snowflake-cli

Works in PowerShell, Windows Terminal or Command Prompt. The lab commands are identical on Windows -- only the shell prompt differs.

Install Snowflake CLI in an isolated tool environment using an approved uv or pipx installation. Do not install into your distribution's system Python.

uv tool install snowflake-cli
# Alternatively:
pipx install snowflake-cli
pipx ensurepath

Open a new shell after PATH changes. See current supported Python versions and platform installation options. A browser-only attendee can instead run setup SQL in Snowsight; local PUT commands require a local client or a stage-upload UI.

Confirm it works:

snow --version

5. Create and test a connection

The labs all take a -c <connection-name> argument. Create one interactively:

snow connection add

You will be asked for a connection name, your account identifier, user, and how you authenticate. Then test it -- do not skip this:

snow connection test -c <your-connection-name>

A working connection prints your account, user, role and warehouse. Optionally make it the default so you can drop the -c flag:

snow connection set-default <your-connection-name>

If your account requires MFA, you will be prompted on every single command, which is miserable during a workshop. Enable MFA caching so you authenticate once every four hours -- see multi-factor authentication. Alternatively use key-pair authentication.

Connections live in ~/.snowflake/config.toml on macOS/Linux (or a platform configuration directory) and %USERPROFILE%\.snowflake\config.toml on Windows. Run snow --info to see the exact path your installation uses.

6. Verify everything, once

This step is yours to run, and it is the one we cannot do for you. Your workshop facilitator has no login in your Snowflake account, so the only way anyone finds out which labs your account supports is if you run this check and send back the output. Please do it well before the session — a few days at least, so there is time to fix anything it flags.

Every attendee should run it under their own login, not just whoever administers the account. Privileges belong to roles: a clean run as ACCOUNTADMIN says nothing about whether the role you will actually use on the day can create a database. Paste the full output back to your facilitator rather than summarising it — the detail is what determines which labs get run.

The prerequisite checker is read-only. Run its statements separately and retain errors as evidence; empty telemetry is not the same as missing access. Then run the separate role smoke test under the actual attendee role.

git clone <workshop-repo-url>
cd coco-interactive-workshop
snow sql -f shared/00_prereqs_check.sql -c <your-connection-name>

The script has two parts:

  • Environment and model checks print account, role, cross-region configuration and available models without invoking a paid AI function.
  • Optional telemetry probes test view access; failures may reflect missing grants or feature availability, not necessarily edition. The separate role smoke test exercises creation and cleanup.

Advanced CLI, extensions and bundled-skill labs

Labs 81-86 and 91-95 have no SQL bootstrap in their core routes. Use an approved CoCo connection for inference and a separate local practice folder. Optional live routes follow the linked data lab's privileges, setup and cleanup.

  • Check cortex --version, cortex --help and cortex exec --help. Desktop users should also inspect their version and Agent Settings skill/plugin/MCP/subagent inventory.
  • Install Python 3.10 or newer for the synthetic practice kit. It uses only the standard library; use python3 on macOS/Linux or py -3 in Windows PowerShell.
  • Ask IT whether local MCP, plugins and subagents are permitted. Missing or disabled features are a documented limitation, not a reason to bypass policy.
  • Do not paste tokens into configs, overwrite existing global settings, or enable unrelated MCP servers. Inspect plugin components before loading them. Keep normal tool approvals enabled.
  • CLI and Desktop do not have identical command storage or controls. Follow each lab's route and verify actual skill/tool invocation; a plausible answer is not evidence that a component ran.

The customer package includes shared/extension_lab/: inert starter templates, synthetic fixtures, a read-only stdio MCP server and local checks. Run its initializer only with a new destination; it refuses existing folders and performs no account operations.

Troubleshooting

SymptomCause and fix
No CoCo in Snowsight, or it will not respond Missing Cortex/CoCo role grants, a surface limit of 0, model access or permitted inference regions can each block access. Check the actual surface and role rather than assuming one cause.
Model "..." is unavailable Cortex is reachable but that model is not available to your account or region. Enabling ANY_REGION gives the widest selection.
cortex: command not found Installed to ~/.local/bin, not on PATH. See step 3.
snow: command not found Open a new terminal after installing. If it persists, the Python tool path is not on PATH.
Prompted for MFA on every command Enable MFA caching, or switch to key-pair authentication. See step 5.
Insufficient privileges when a lab sets up Check the active role in CoCo and SQL separately; missing warehouse creation, object ownership, Cortex access or an optional bundle can also cause this. Run the role smoke test in step 1.
Invalid identifier 'INFORMATION_SCHEMA...' Only appears if you hand-write a query against a table function without a database qualifier. The lab scripts already handle it.
PowerShell blocks the install script Set the execution policy for the current process only. See step 3.

A note on the two CLIs, and on the name

Two things routinely confuse people:

  • snow is the Snowflake CLI -- it runs SQL and manages Snowflake objects. cortex is the CoCo CLI -- it is the agent. The labs use both, and they are installed separately.
  • CoCo was called Cortex Code until Snowflake Summit on 2 June 2026. Same product. Documentation URLs, the CORTEX_CODE_* account parameters and the CORTEX_CODE_*_USAGE_HISTORY views all still use the old name, so expect to see both.
